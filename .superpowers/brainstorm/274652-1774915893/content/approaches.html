RC Mission Control — Architecture Approaches

How should the Orin read RC channel switches and trigger mission commands?

A

mavlink_interface_node reads RC_CHANNELS directly

Add RC channel monitoring to the existing mavlink_interface_node. It already owns the pymavlink connection, so it can read RC_CHANNELS messages and call the StartMission/ResumeMission services internally when channels 14/15 cross a threshold (e.g., PWM > 1700).

Pros

  • No new nodes — minimal code change
  • mavlink_interface already has the pymavlink connection
  • Single source of truth for all MAVLink interaction
  • RC channels are broadcast at high rate (~50Hz) by ArduPilot

Cons

  • Adds responsibility to an already busy node
  • mavlink_interface becomes aware of mission concepts (start/resume)
B

New rc_mission_trigger_node

A small, dedicated node that subscribes to a new /dbvf/rc_channels topic (published by mavlink_interface) and watches channels 14/15. When triggered, it calls the existing ROS2 services (/dbvf/start_mission, /dbvf/resume_mission).

Pros

  • Clean separation of concerns
  • mavlink_interface stays MAVLink-only
  • Easy to test the trigger logic independently

Cons

  • New node + new topic = more moving parts
  • Requires mavlink_interface to publish RC channels (new topic)
  • Extra hop adds small latency (negligible in practice)
C

mission_sequencer_node reads RC directly via pymavlink

Give the mission sequencer its own secondary pymavlink connection (read-only) to monitor RC channels, keeping the trigger logic in the same node that manages mission state.

Pros

  • Trigger logic lives next to mission logic
  • No cross-node service calls needed

Cons

  • Breaks the "single pymavlink owner" pattern
  • Second MAVLink connection adds complexity
  • Goes against existing architecture decisions

Recommendation: Option A

The mavlink_interface_node already reads every MAVLink message from the Cube Orange. Adding a check for RC_CHANNELS is ~30 lines of code. The "added responsibility" concern is minor — it's just edge-detecting two channels and calling two services. No new nodes, no new topics, no architectural changes.
