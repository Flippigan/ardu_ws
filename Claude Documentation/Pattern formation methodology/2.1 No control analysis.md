## Executive Summary

### 🚨 **Primary Issue Identified: ArduPilot Lacks Native Multi-Swarm Functions**

**Root Cause**: ArduPilot's source code does not have built-in functions for multi-swarm operations. Each SITL instance operates independently without awareness of other drones, publishing to the same global DDS namespace.

**Critical Impact**:
- All drones publish to identical topics (`/ap/pose/filtered`) instead of drone-specific namespaces
- Formation control cannot distinguish between individual drones
- Requires external coordination layer (ROS2 formation control nodes) to achieve multi-drone operations


## Multi-Swarm Limitation Analysis

### 🚨 **ArduPilot Source Code Constraints**

#### Limitation 1: Global DDS Topic Space
- **Issue**: Each ArduPilot instance publishes to identical topics
- **Evidence**: All drones use `/ap/pose/filtered` regardless of namespace configuration
- **Impact**: Formation control sees all drones as a single entity

#### Limitation 2: No Inter-Drone Communication
- **Issue**: ArduPilot has no built-in swarm coordination protocols
- **Evidence**: No topics like `/swarm/formation` or `/fleet/coordination`
- **Impact**: Requires external ROS2 layer for formation intelligence

#### Limitation 3: Single-Vehicle Design Philosophy
- **Issue**: ArduPilot designed for individual vehicle autonomy
- **Evidence**: No multi-vehicle parameters or collision avoidance
- **Impact**: Cannot leverage ArduPilot's built-in flight modes for formation flying

## Solutions and Workarounds

### Option 1: Topic Remapping (Immediate Fix)
**Approach**: Use ROS2 topic remapping to create drone-specific namespaces
```python
# Add to launch file for each drone
Node(
    package="topic_tools",
    executable="relay",
    arguments=["/ap/pose/filtered", "/iris_9002/ap/pose/filtered"],
    namespace="iris_9002",
    condition=IfCondition(some_condition_to_make_this_drone_specific)
)
```

**Pros**: Quick implementation, preserves ArduPilot functionality
**Cons**: Additional processes, potential message delays

### Option 2: Formation Control Adaptation (Recommended)
**Approach**: Modify formation control to use global topics with drone identification
```python
# Formation control subscribes to single topic
/ap/pose/filtered  # All drones publish here

# Use ArduPilot message fields to distinguish drones:
def pose_callback(self, msg):
    drone_id = self.identify_drone(msg)  # Via timestamp, position, or system_id
    self.update_drone_position(drone_id, msg)
```

**Pros**: Works with ArduPilot as-is, efficient message flow
**Cons**: Requires drone identification logic

### Option 3: ArduPilot Source Modification (Advanced)
**Approach**: Modify ArduPilot DDS implementation to respect namespaces
```cpp
// In ArduPilot DDS client code
std::string topic_prefix = get_namespace_parameter();
std::string full_topic = topic_prefix + "/ap/pose/filtered";
```

**Pros**: Proper namespace isolation, clean architecture
**Cons**: Requires ArduPilot expertise, maintenance burden
