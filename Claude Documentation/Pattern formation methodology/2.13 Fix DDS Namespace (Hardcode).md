# ArduPilot DDS Simplified Instance Methodology
**Hardcoded Unique Identifier Approach for Multi-Instance SITL**

## Executive Summary

This document presents a **simplified hardcoded approach** for enabling individual instance namespacing in ArduPilot's DDS system. Instead of complex dynamic name generation, this methodology uses **compile-time unique identifiers** that are set once per build, making the implementation much simpler and more reliable.

**Document Version:** 1.0
**Target ArduPilot Version:** 4.5+
**Implementation Complexity:** **LOW**
**Approach:** Hardcoded instance identifiers in source code

---

## Simplified Problem & Solution

### Problem
All SITL instances use identical DDS topic/service names, causing namespace collisions.

### Simple Solution
**Hardcode a unique instance identifier** into each ArduPilot build that gets compiled into the topic/service names.

```cpp
// Instead of complex runtime detection, use simple hardcoded value:
#define AP_DDS_INSTANCE_ID 0  // Set this to 0, 1, 2, 3, 4 for each build

// Results in:
Instance 0 build: "rt/ap_0/pose/filtered"
Instance 1 build: "rt/ap_1/pose/filtered"
Instance 2 build: "rt/ap_2/pose/filtered"
```

---

## Implementation Strategy

### Two Simple Approaches

#### **Approach A: Compile-Time Definition (Recommended)**
- Add `#define AP_DDS_INSTANCE_ID N` to build system
- Modify topic/service names using string concatenation macros
- **Pros:** Simplest, no runtime overhead, no memory allocation
- **Cons:** Requires separate builds for each instance

#### **Approach B: Single Parameter Change**
- Add one parameter to `AP_DDS_config.h`
- Manually change value and rebuild for each instance
- **Pros:** Single file modification, still very simple
- **Cons:** Manual parameter editing required

## Approach A: Compile-Time Definition (RECOMMENDED)

### Step 1: Add Build System Definition

**File:** `wscript` or build command line

```bash
# Build commands for each instance
./waf configure --board sitl -D AP_DDS_INSTANCE_ID=0  # Instance 0
./waf configure --board sitl -D AP_DDS_INSTANCE_ID=1  # Instance 1
./waf configure --board sitl -D AP_DDS_INSTANCE_ID=2  # Instance 2
./waf configure --board sitl -D AP_DDS_INSTANCE_ID=3  # Instance 3
./waf configure --board sitl -D AP_DDS_INSTANCE_ID=4  # Instance 4
```

### Step 2: Add Default Definition

**File:** `AP_DDS_config.h` (add at end, around line 173)

```cpp
// Instance ID for multi-vehicle DDS support
#ifndef AP_DDS_INSTANCE_ID
#define AP_DDS_INSTANCE_ID 0  // Default to instance 0
#endif

// Helper macros for string concatenation
#define AP_DDS_STR_HELPER(x) #x
#define AP_DDS_STR(x) AP_DDS_STR_HELPER(x)
#define AP_DDS_INSTANCE_STR AP_DDS_STR(AP_DDS_INSTANCE_ID)

// Topic name generation macros
#define AP_DDS_TOPIC(name) "rt/ap_" AP_DDS_INSTANCE_STR "/" name
#define AP_DDS_SERVICE(name) "rs/ap_" AP_DDS_INSTANCE_STR "/" name
#define AP_DDS_REQUEST(name) "rq/ap_" AP_DDS_INSTANCE_STR "/" name
#define AP_DDS_REPLY(name) "rr/ap_" AP_DDS_INSTANCE_STR "/" name
```

### Step 3: Update Topic Table

**File:** `AP_DDS_Topic_Table.h`

Replace hardcoded strings with macro calls:

### Step 4: Update Service Table

**File:** `AP_DDS_Service_Table.h`

## Approach B: Single Parameter (Alternative)

### Simple Parameter Method

**File:** `AP_DDS_config.h` (add at end)

```cpp
// Simple instance ID - manually change for each build
#ifndef AP_DDS_INSTANCE_ID
#define AP_DDS_INSTANCE_ID 0  // CHANGE THIS: 0, 1, 2, 3, 4 for each instance
#endif

// Rest of macro definitions same as Approach A...
```

**Usage:**
1. Change `#define AP_DDS_INSTANCE_ID 0` to desired instance number
2. Rebuild ArduPilot: `./waf copter`
3. Deploy to specific SITL instance

### Automated Build Script


## Advantages of Simplified Approach

### **Development Benefits**
- ✅ **Simple Implementation** - Only string replacements needed
- ✅ **No Runtime Logic** - Zero performance overhead
- ✅ **No Memory Allocation** - All strings are compile-time constants
- ✅ **Predictable Behavior** - No runtime detection or parameter parsing
- ✅ **Easy Debugging** - Topic names visible in source code

### **Operational Benefits**
- ✅ **Reliable** - No dynamic failures or edge cases
- ✅ **Fast Build** - Macro expansion only, no complex logic
- ✅ **Clear Separation** - Each instance is a completely separate build
- ✅ **Version Control Friendly** - Easy to track which build is which instance

### **Maintenance Benefits**
- ✅ **Minimal Code Changes** - Only 2-3 files modified
- ✅ **No New Dependencies** - Uses existing C preprocessor
- ✅ **Backward Compatible** - Default behavior unchanged
- ✅ **Easy Rollback** - Simple to revert changes

---

## Disadvantages (Trade-offs)

### **Build Process**
- ❌ **Multiple Builds Required** - Need separate build for each instance
- ❌ **Build Time** - 5x build time for 5 instances
- ❌ **Storage** - 5 separate executables instead of 1

### **Deployment**
- ❌ **Manual Management** - Need to track which executable is which instance
- ❌ **No Runtime Flexibility** - Instance ID fixed at compile time

### **Development Workflow**
- ❌ **Source Code Coordination** - Multiple developers need build discipline
